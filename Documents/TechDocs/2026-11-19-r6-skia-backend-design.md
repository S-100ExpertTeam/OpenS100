# R6: Skia 백엔드 설계

2026-11-19 작성. 사용자 요청: "R6 Skia 설계". [렌더 분리 설계](2026-11-17-render-separation-design.md)의 R6 행("Skia로 `IRenderer` 구현, D2D 결과와 허용 오차로 비교, 통과하면 D2D 제거")을 구체화한다. 지침 24(Skia 단일 백엔드, D2D는 전환기 기준으로 최소한만 손댄다), 22·25(SOLID·현대 C++), 23(화면 검증)을 따른다.

**상태: 5절의 다섯 가지는 2026-11-19에 권고대로 정해졌다("권고대로 시작"). R6-0 완료, 다음은 R6a. 진행은 8절에 적는다.**

## 1. 지금 있는 것과 없는 것

R5까지로 "무엇을 어디에"는 공용 코드(`DisplayListPainter`)가 정하고, 808개 셀에서 Windows와 Linux가 같은 호출 열을 낸다(해시 동일). 남은 것은 원시 연산 열 개(`IRenderer.h`)를 Skia로 구현하는 일인데, 그중 셋은 "백엔드가 모양을 안다"로 남겨 둔 것이라 구현할 양이 크다.

| `IRenderer` 연산 | Skia로 옮길 때 | 판단 |
|---|---|---|
| `SetTransform` | `SkMatrix`를 단계별로 곱한다 | 쉬움 |
| `StrokePath`(경로·보관 경로), `Retain` | `SkPath`(`SkPathBuilder`), `SkPaint` 긋기. 굵기는 장치 픽셀 고정이라 변환의 배율로 나눠 준다. 점선은 `SkDashPathEffect`(굵기의 배수 → 절대 길이) | 쉬움 |
| `FillPath` 색 | 짝홀 규칙, 안티에일리어싱 끔 | 쉬움 |
| `MeasureText`, `FillText` | `SkFont`. **서체를 어디서 가져올지가 결정 사항**(5절 2) | 중간 |
| `DrawSymbol` | **심벌을 읽어 그리는 코드가 Windows에만 있다** | 큼 |
| `FillPath` 무늬(카탈로그 면 채움, 심벌 타일) | 위와 같은 심벌 코드 + 타일 만들기 | 중간(심벌 뒤) |
| `StrokeLineStyle` | 선 스타일 띠를 만들고 선을 따라 까는 코드가 Direct2D에 묶여 있다 | 큼 |

### 1.1 Direct2D 백엔드가 기대는 것 (조사 결과)

- **심벌**: `S100Engine/SVGReader`가 카탈로그 SVG를 읽어 `ID2D1PathGeometry`로 만든다. 읽는 범위가 좁다 — `<svg>`의 직계 자식만 보고, `path`는 절대 좌표 `M`/`L`만, 그 밖에 `rect`(레이아웃 상자와 일반 사각형), `circle`(피벗과 일반 원)이다. 곡선·호·상대 좌표·`<g>` 중첩·`line`/`polyline`/`polygon`/`ellipse`·`transform`·`stroke-dasharray`는 읽지 않거나 읽고 쓰지 않는다. 색은 `class`의 마지막 낱말(`f`로 시작하면 채움, 아니면 긋기, 나머지가 색 토큰)을 그릴 때 현재 팔레트로 푼다. 긋기 굵기는 mm × 0.03937 × 96 픽셀로 고정(확대해도 그대로), 심벌 배율은 픽셀/mm. 없는 심벌은 `QUESMRK1`로 그린다.
- **선 스타일**: 스타일마다 띠 한 장을 WIC 비트맵으로 미리 그린다(대시는 1픽셀 선 — 펜 굵기를 쓰지 않는다, 심벌은 위의 심벌 그리기). `S100Render::DrawBitmapOnLine`이 선분마다 회전 변환을 걸고 띠를 반복해 붙인다. 선분 길이가 띠 길이의 정확한 배수면 그 선분을 그리지 않고, 20픽셀보다 짧으면 가는 점선으로 대신한다. 화면 밖 선분을 걸러내지 않는다.
- **면 채움 무늬**: 격자 벡터로 타일 크기를 정해 심벌을 모서리 4곳(또는 5곳)에 그린 WIC 비트맵을 반복 브러시로 쓴다(최근접 샘플링). 팔레트가 바뀌면 다시 만든다.
- **텍스트**: DirectWrite, 서체는 뷰어 설정의 표시 서체(기본 "Malgun Gothic"), 보통 굵기, 정체 또는 이탤릭. 크기는 정수로 버린다.
- **표면**: `ID2D1DCRenderTarget` 하나. 뷰어는 `HDC`에 그리고, 그림 테스트(`RenderSmoke`)는 GDI DIB에 그려 GDI+로 PNG를 쓴다.
- **빌드**: 위의 것(`S100Engine` 전체, `D2DRenderer`, `LayerManager`)은 CMake 타깃에 없다. Visual Studio 솔루션에서만 빌드된다. `IRenderer.h`와 `DisplayListPainter`는 `opens100::portrayal`에 있다.

### 1.2 이미 플랫폼 중립인 것

- 색 프로파일: `S100_ColorProfile::ReadFile`(`portrayalcatalogue`).
- 선 스타일 XML: `PortrayalCatalogue::GetLineStylesByPugiXml` → `S100_LineStyle`, `S100_CompositeLineStyle`.
- 심벌 채움 XML: `S100_SymbolFill::ReadFileByPugiXml`.
- **없는 것: 중립 SVG 읽기.** `Portrayal::ResourceStore`는 파일 경로만 넘기는 인터페이스이고 구현은 `S100PCManager`(Windows) 하나다.

### 1.3 `IRenderer`를 거치지 않는 Direct2D 그리기

Skia가 인스트럭션을 다 그려도 아래가 남아 있으면 D2D를 뺄 수 없다. R6의 범위가 아니고 R7(6절)에서 다룬다.

| 어디 | 무엇 | 옮기려면 필요한 것 |
|---|---|---|
| `LayerManager` | 프레임 시작·끝, 셀·우선순위 순회 | 순회를 중립 코드로(3.5) |
| `DepthSuppression` | S-98 수심 가림(`PushLayer` 지오메트리 마스크) | `IRenderer`에 클립 |
| `CoverageDataset` | S-102·S-104 래스터, 등심선, S-111 화살표 | `IRenderer`에 이미지 그리기 |
| `S100ExchangeCatalogue` | 교환 세트 범위 외곽선과 글자 | 지금 있는 연산으로 가능 |
| `S100EditRender` | 편집 꼭짓점 손잡이 | 지금 있는 연산으로 가능 |
| `ExchangeCatalogue`, `GISLibrary::DrawScaleBar`, `S100Render::DrawScale`, `BackgroundLayer` | 부르는 곳이 없거나 주석 처리됨 | 지운다 |

## 2. vcpkg의 Skia 포트

로컬 vcpkg(기준선 `6cf5a361`, 이 저장소의 `builtin-baseline`과 같다)의 `ports/skia`를 읽었다.

- 버전 148. 지원: `!(windows & arm32) & !mingw`. CMake 타깃 `unofficial::skia::skia`, 모듈은 `unofficial::skia::modules::*`.
- 기본 기능이 무겁다: `dng`, `fontconfig`(Linux), `freetype`(Windows·macOS 제외), `gl`, `harfbuzz`, `icu`, `jpeg`, `png`, `webp`.
- **기본 기능을 끄고 필요한 것만 켠다**: `png`(그림을 파일로 쓸 때), 그리고 서체 결정(5절 2)에 따라 `freetype`(+ Linux에서 시스템 서체를 쓴다면 `fontconfig`). GPU(`gl`·`vulkan`·`direct3d`·`metal`)는 켜지 않는다 — 3.1.
- `harfbuzz`·`icu` 없이는 글자 조합(아랍 문자, 인도계 문자)과 양방향 배치가 안 된다. 한글·한자·라틴 문자는 글리프를 하나씩 놓는 것으로 된다. DirectWrite는 지금 조합을 해 주므로, 이것은 **Skia 쪽이 잃는 기능**이다. 나중에 포트 기능 하나(`render-skia-shaping`)로 더한다.
- Skia 148은 `SkPath`를 고칠 수 없는 값으로 바꾸는 중이다(Milestone 144 릴리스 노트: 경로는 `SkPathBuilder`나 팩토리로 만든다). 처음부터 `SkPathBuilder`만 쓴다.
- **잰 것(R6a, 2026-11-20)**: `skia[core,freetype,png]`의 빌드는 이 PC(x64-windows, 디버그+릴리스)에서 4.7분, Docker의 Ubuntu 24.04(x64-linux)에서 3.9분. 저장소 매니페스트 전체를 `render-skia`와 함께 처음 설치하는 데 7.2분(다른 의존성은 캐시에서). `skia.dll` 5.6 MB. 딸려 오는 것: abseil, expat, freetype(+ bzip2, brotli, libpng, zlib), Windows에서 dlfcn-win32와 opengl(레지스트리 헤더). 예상보다 훨씬 가볍다 — GPU·ICU·HarfBuzz를 뺀 덕이다.
- **서체 관리자(R6c에서 확인)**: `SkFontMgr_New_Custom_Empty()`(`include/ports/SkFontMgr_empty.h`)로 시스템 서체가 없는 FreeType 관리자를 만들고 `makeFromData`로 서체 파일을 읽는다. Windows에서도 같은 길이다(DirectWrite 관리자를 쓰지 않는다).

## 3. 설계

### 3.1 표면은 응용 프로그램의 것, 렌더러는 `SkCanvas`만 받는다

```cpp
namespace s100::render {
    class SkiaRenderer final : public IRenderer {
    public:
        SkiaRenderer(SkCanvas& canvas, const SkiaResources& resources);
        // IRenderer ...
    };
}
```

- 렌더러는 캔버스가 CPU 래스터인지 GPU인지 모른다. 표면을 만들고 화면에 내는 일은 부르는 쪽이 한다(단일 책임, 의존 역전).
- **R6는 CPU 래스터만 쓴다.** 이유: (1) 지금 기준 그림이 소프트웨어 렌더(`S100_RENDER_SOFTWARE`)라 비교 대상이 같다. (2) GPU 백엔드는 플랫폼마다 다르고(GL·Vulkan·Metal·D3D) 패키지 의존성을 키운다. (3) 뷰어는 지금도 `HDC`에 그린다 — Skia 래스터 표면을 DIB 메모리 위에 만들면 `Draw(HDC)` 계약을 그대로 둘 수 있다. GPU는 응용 프로그램이 캔버스를 그렇게 만들면 되는 일이고, 필요해질 때 속도를 재고 정한다.
- 색 공간은 지정하지 않는다(sRGB 값을 그대로 섞는다). Direct2D가 지금 그렇게 한다.
- 글자 안티에일리어싱은 회색조. LCD 부화소는 쓰지 않는다(표면과 화면에 따라 달라진다).

### 3.2 심벌·선 스타일·무늬: 중립 모델을 새로 쓰고, 그리기는 `IRenderer`의 경로 연산으로 내린다 (권고)

지금 `DrawSymbol`·`StrokeLineStyle`·무늬 채움은 "백엔드가 모양을 안다". Skia 백엔드에 같은 것을 한 번 더 쓰면 S-100 로직이 둘이 된다(R5가 없앤 것). 선택지:

| | (가) 중립 심벌 모델 + 공용 그리기 | (나) Skia의 SVG 모듈(`SkSVGDOM`) |
|---|---|---|
| SVG 읽기 | pugixml로 직접(이미 의존성). 카탈로그 SVG는 S-100 Part 9가 정한 좁은 부분집합(SVG Tiny) | Skia가 읽는다 |
| 색 토큰 | `class` → 토큰 → 팔레트를 그릴 때 푼다(지금과 같은 방식) | CSS를 팔레트마다 만들어 SVG에 끼워 다시 읽는다(웹 구현의 방식) |
| 굵기 고정(확대해도 그대로) | 우리 코드라 그대로 | SVG에는 없는 규칙이라 따로 손봐야 한다 |
| D2D와 같은 그림 | 높다(같은 모델, 같은 규칙) | 낮다 |
| 의존성 | 없음 | Skia 모듈 svg(+ 그 의존) |
| 다른 백엔드(미래) | 그대로 쓴다 | Skia 전용 |

**권고 (가).** 새 중립 모델 `SymbolPicture`(도형 목록: 닫힌·열린 꺾은선, 원, 각각 채움/긋기·색 토큰·굵기 mm·투명도, 그리고 상자와 피벗)를 `opens100::portrayal` 옆에 두고, 그리는 일은 공용 코드가 `IRenderer`의 `FillPath`·`StrokePath`(+ 원)로 한다. Skia 백엔드는 심벌이 무엇인지 모른다.

- D2D 쪽은 건드리지 않는다. `D2DRenderer::DrawSymbol`은 지금처럼 `S100PCManager`로 그린다(지침 24: 최소한으로). `IRenderer`의 `DrawSymbol`·`StrokeLineStyle`·무늬 `Fill`은 D2D를 뺄 때(R7) 인터페이스에서 사라지고 페인터 안으로 들어간다. 그때까지는 Skia 백엔드가 이 세 연산을 받아 공용 코드(`SymbolPainter`, `LineStylePainter`, `PatternTile`)에 넘긴다 — 얇은 전달이다.
- **읽는 범위**: 먼저 지금 `SVGReader`와 **같은 범위**로 읽는다(비교가 의미 있으려면). 넓히는 것(곡선, `<g>`, `polyline` 등)은 따로 한다 — 카탈로그 심벌 중 지금 빠지고 그려지는 것이 있는지 먼저 세어 본다(세지 않았다).
- **무늬 타일**: 타일을 `SkPicture`로 기록해 반복 셰이더로 쓴다(벡터라 확대에 흐려지지 않는다). 무늬는 장치 픽셀 고정이므로 셰이더의 지역 행렬에 현재 변환의 역을 준다(D2D 백엔드와 같은 규칙).
- **선 스타일**: 띠를 비트맵이 아니라 "대시와 심벌의 배치"로 두고, 선분을 따라 놓는 계산(`LineStylePainter`)이 `StrokePath`와 심벌 그리기를 부른다. 5절 4의 결정에 따라 지금 D2D의 버릇을 따를지 정한다.

### 3.3 텍스트

`TextFont`는 크기와 기울임만 갖고 서체는 백엔드의 것이다(`IRenderer.h`). Skia 백엔드는 `SkiaResources`로 서체를 받는다.

- 서체에 없는 글자는 다음 서체에서 찾는다(목록 순서). DirectWrite가 해 주던 대체를 직접 한다.
- `MeasureText`의 값이 DirectWrite와 다르면 글자 위치(가운데·오른쪽 맞춤)가 달라진다. 같은 서체 파일이면 글자 폭은 거의 같고, 높이(줄 높이를 무엇으로 볼지)는 맞춰야 한다 — 어센트 + 디센트 + 줄 간격으로 시작하고 D2D 값과 대조해 고친다.
- 크기는 D2D처럼 정수로 버린다(지금 그림과 맞추기 위해. 렌더 분리 설계 9.3절의 "버림" 항목은 그대로 남는다).

### 3.4 보관 경로의 주인

`DisplayListPainter`는 곡선·면 경로를 지오메트리의 칸(`renderAttachment`)에 한 번 만들어 둔다. 두 백엔드가 같은 데이터셋을 그리면(비교 테스트) Skia 페인터가 D2D가 만든 경로를 집어 `SkiaRenderer`에 넘기고, 백엔드는 "남의 경로는 그리지 않는다"로 **아무것도 안 그린다**. 설계 문서 3.1이 미리 적어 둔 한계다.

**고친다(R6a)**: 칸에 경로를 만든 렌더러를 같이 적고, 다르면 다시 만든다. 비교 테스트는 데이터셋 하나에 두 백엔드를 번갈아 돌리지 않고 한 백엔드로 끝까지 그린 뒤 다음으로 넘어가면 다시 만드는 일이 한 번뿐이다.

### 3.5 그리기 순회를 중립 코드로

Linux에서 그림을 내려면 "어떤 인스트럭션을 어떤 순서로"가 중립이어야 한다. 지금 그 순회는 `LayerManager`(Windows, MFC)에 있고, 소비자 예제와 테스트는 디스플레이 리스트를 저장 순서로 돈다(그림용 순서가 아니다).

- `LayerManager::DrawS100Layers`의 순회(우선순위 → 레이어 → 종류)를 `opens100::portrayal`의 함수 하나로 옮기고 `LayerManager`가 그것을 부른다. **D2D 그림은 동일해야 한다**(808개 셀).
- R4b(표시면까지 넣은 셀 간 병합 정렬)가 손대는 자리와 같다. R6에서는 순서를 **바꾸지 않고 옮기기만** 한다. R4b는 그 함수 하나를 고치는 일이 된다.
- 수심 가림(`DepthSuppression`)은 클립이 필요해 R6의 Skia 그림에는 빠진다. KOR TDS 808개 셀 비교는 가림이 켜지지 않는 조건이라 영향이 없는지 **확인해야 한다**(확인하지 않았다).

### 3.6 타깃과 포트 기능

```
opens100::portrayal      IRenderer.h, DisplayListPainter, (새) SymbolPicture·SymbolPainter·
                         LineStylePainter·PatternTile, 그리기 순회        ← Skia를 모른다
opens100::render-skia    SkiaRenderer, SkiaResources, PNG 쓰기 도우미      ← unofficial::skia::skia
```

- CMake 옵션 `OPENS100_BUILD_RENDER_SKIA`(기본 OFF), 포트 기능 `render-skia`(기본 기능 아님, `portrayal`에 의존, `skia`는 `default-features: false`).
- Visual Studio 솔루션: `OpenS100Tests`가 `render-skia`를 링크해 같은 프로세스에서 D2D와 Skia 그림을 낸다. 뷰어(`OpenS100`)는 R6에서 바꾸지 않는다.
- 소비자 예제: `--png` 같은 선택 인자로 셀 하나를 그려 파일로 쓴다. Linux에서 처음 나오는 그림이 된다.

## 4. 검증: "같은 그림"을 무엇으로 볼 것인가

Skia와 Direct2D는 안티에일리어싱과 글자 래스터가 달라 바이트 단위로 같을 수 없다. 대신 층을 나눠 본다.

1. **호출 열**(이미 있음): 기록 렌더러 해시가 플랫폼 간에 같다. Skia가 틀리면 원시 연산이 틀린 것이다.
2. **연산별 작은 그림**: 연산 하나만 쓰는 작은 장면(색 채움, 실선, 점선, 호, 회전된 심벌, 무늬, 글자)을 두 백엔드로 그려 비교한다. 어긋남의 원인이 한눈에 보인다.
3. **종류별 셀 그림**: 808개 셀을 면만·선만·심벌만·글자만 그려 종류마다 비교한다(방문자에서 종류를 거르는 것으로 된다). 전체 그림도 비교한다.
4. **사람이 본다**(지침 23): 차이가 큰 순으로 셀을 골라 D2D·Skia·차이 그림을 나란히 놓은 쪽을 만들어 사용자가 본다.

비교 수치(셀마다):
- **달라진 픽셀 비율**: 어느 채널이든 16/255 넘게 다른 픽셀의 비율.
- **1픽셀 어긋남을 봐준 비율**: 상대 그림의 3×3 이웃 안에 가까운 색이 있으면 같은 것으로 친다. 안티에일리어싱 차이는 여기서 사라지고, 빠진 도형·틀린 색·틀린 위치는 남는다.

**허용 오차는 미리 정하지 않는다.** 첫 측정(R6a의 색 채움과 실선)에서 분포를 보고 종류별 기준을 이 문서에 적는다. 예상(재 본 것 아님): 안티에일리어싱 없는 채움은 경계 한 줄 안팎으로 거의 같고, 긋기는 가장자리 픽셀만, 글자가 가장 다르다.

**플랫폼 간 Skia 그림**: 같은 Skia라도 CPU 명령 집합과 부동소수점 경로에 따라 픽셀이 다를 수 있다. Windows와 Linux의 Skia 그림도 위와 같은 수치로 비교하고, 바이트 동일은 기대하지 않는다.

**성능**: `RenderSmoke`의 시간(첫 그리기, 다음 4프레임)을 Skia로도 낸다. D2D 소프트웨어 렌더(150개 셀 다음 4프레임 17.95 s)가 기준이다. 목표 수치는 첫 측정 뒤에 정한다.

## 5. 결정 (2026-11-19, 모두 권고대로)

1. **심벌·선 스타일·무늬를 어떻게 그릴지** — 권고: (가) 중립 모델을 새로 쓰고 공용 코드가 경로 연산으로 그린다(3.2). 대안: Skia의 SVG 모듈.
2. **서체를 어디서 가져올지**
   - (A) 플랫폼의 서체 관리자(Windows는 DirectWrite, macOS는 CoreText, Linux는 fontconfig)에서 이름으로 찾는다. Windows에서 지금 그림과 가장 가깝다. 플랫폼마다 그림이 다르고, 설치된 서체에 달렸다. Linux는 `fontconfig` 의존이 붙는다.
   - (B) **권고**: 응용 프로그램이 서체 파일을 넘긴다(순서 있는 목록, 대체용 포함). 전 플랫폼에서 FreeType으로 읽는다. 플랫폼 간 그림이 가장 가깝고, 설치된 서체에 기대지 않고, WASM에서도 같다. 뷰어는 설정의 서체 이름을 파일로 바꿔 넘겨야 한다(Windows 서체 폴더에서 찾기). 패키지는 서체를 싣지 않는다 — "Malgun Gothic"은 재배포할 수 없고, 저장소에 있는 것은 일부 카탈로그의 Droid Sans·Open Sans(한글 없음)뿐이다.
   - 테스트용 서체: (B)라면 저장소의 Open Sans로 글자 테스트를 고정할 수 있다(한글은 따로).
3. **R6가 어디서 끝나는지** — 권고: "Skia가 808개 셀을 화면 없이 그리고, D2D와의 차이가 정한 기준 안이며, Linux에서도 그림이 나온다"까지. 뷰어를 Skia로 바꾸고 1.3의 직접 그리기를 옮겨 D2D를 지우는 일은 R7로 뗀다.
4. **지금 D2D의 버릇을 따를지** — 권고: 그림의 의도는 따르고, 명백한 결함은 고치며, 고친 것은 "알려진 차이"로 적어 비교에서 구분한다. 해당하는 것:
   - 선 스타일: 선분 길이가 띠 길이의 정확한 배수면 그리지 않는다(결함으로 본다 → 그린다).
   - 선 스타일: 대시를 펜 굵기와 무관하게 1픽셀로 그린다(카탈로그의 굵기를 따르면 그림이 눈에 띄게 달라진다 → **먼저 1픽셀로 맞추고**, 굵기 반영은 따로 묻는다).
   - 선 스타일: 띠가 선분마다 처음부터 다시 시작한다(꺾이는 곳에서 무늬가 끊긴다 → 먼저 그대로).
   - 렌더 분리 설계 9.3절의 면·선·텍스트 항목(해치·픽스맵 채움 없음, 글자 크기 버림 등)은 공용 페인터의 것이라 Skia에서도 그대로다.
5. **의존성 범위** — 권고: `skia[core,png]` + (2B라면) `freetype`. GPU·ICU·HarfBuzz·JPEG·WebP·DNG는 뺀다. 글자 조합(아랍·인도계)은 나중 기능으로.

### 5.1 추가 결정 (2026-11-20)

사용자와 R6c 뒤에 정한 것:

6. **D2D는 Windows용으로도 남기지 않는다.** `IRenderer` 뒤에 D2D를 Windows 백엔드로 두는 안을 검토했고 버렸다. 남기면 그림이 두 벌이 되고(이미 다르다: 한 바퀴 호, 심벌 20개의 모서리, 글자의 진하기), 심벌·선 스타일·무늬의 S-100 로직이 `S100Engine`에 한 벌 더 남으며, `IRenderer`에서 `DrawSymbol`·`StrokeLineStyle`·무늬 `Fill`을 내릴 수 없고, 검증이 백엔드마다 든다. 지침 24대로 R7에서 지운다.
7. **GPU는 뷰어의 표면에서 쓴다. 렌더러는 그대로다.** `SkiaRenderer`는 캔버스만 받으므로 CPU 래스터와 GPU가 같은 코드다. CPU 경로는 남긴다 — GPU가 없는 곳(서버, Docker, CI)에서 그림을 내고, 플랫폼 간에 같은 그림으로 검증하고, GPU 초기화가 실패한 PC에서 내려갈 곳이 된다. GPU 백엔드는 포트의 선택 기능으로 둔다(기본 기능에 넣지 않는다).
9. **(R6f의 측정에서 나온 것. 2026-11-24 결정: 저장소에 Skia 오버레이 포트를 둔다 — 8.8)** Windows에서 vcpkg가 MSVC로 빌드한 Skia는 CPU 래스터가 GCC 빌드보다 5.6배 느리다(8.6절). R7에서 뷰어를 Skia로 옮기려면 Windows의 Skia를 clang-cl로 빌드하는 길(포트 오버레이나 트리플렛)을 먼저 내거나, GPU 표면을 기본으로 해야 한다.
8. **순서**: R6는 CPU 래스터로 끝낸다. R6f에서 프레임 시간을 잰다. R7에서 뷰어의 표면을 정할 때 그 수치로 GPU를 기본으로 할지 정하고, Windows에서 쓸 GPU 백엔드(Direct3D·OpenGL·Vulkan)를 조사한다(아직 하지 않았다). 성능이 모자라면 D2D를 되살리는 것이 아니라 Skia 쪽(GPU 표면, 보관 경로의 변환 비용, 심벌 캐시)을 고친다.

## 7. 위험과 모르는 것

- **Skia 빌드**: 시간·크기를 재지 않았다. vcpkg 바이너리 캐시가 없으면 CI와 소비자 쪽 첫 설치가 길어진다. `render-skia`를 기본 기능에서 빼는 이유다.
- **Skia API의 변동**: 버전마다 이름이 바뀐다(경로, 서체 관리자). vcpkg 기준선을 올릴 때마다 `render-skia`가 깨질 수 있다. Skia 헤더를 쓰는 파일을 `SkiaRenderer.cpp` 등 소수로 묶어 둔다(공개 헤더에는 `SkCanvas` 전방 선언만).
- **글자**: 가장 다를 부분. 같은 서체 파일을 써도 DirectWrite와 FreeType의 힌팅·래스터가 다르다. 허용 오차를 글자만 따로 둔다.
- **안티에일리어싱 없는 채움의 경계**: 픽셀 중심이 변에 정확히 걸릴 때의 규칙이 백엔드마다 다를 수 있다. 이웃한 면 사이에 한 줄짜리 틈이나 겹침이 생기는지 연산별 작은 그림으로 먼저 본다.
- **굵기 고정 긋기**: Skia에는 "변환과 무관한 굵기"가 0(헤어라인) 말고는 없다. R6a는 처음부터 **경로를 장치 좌표로 바꿔 긋는다**(`SkPath::makeTransform`) — 굵기와 점선 길이가 그대로 장치 픽셀이다. 보관 경로도 그릴 때마다 변환하므로 비용이 있다. 성능은 R6f에서 재고, 문제면 굵기를 배율로 나누는 방식과 비교한다.
- **macOS**: 이 PC에서 확인할 수 없다. CI는 수동 실행(지침)이라 사용자가 돌려야 한다.
- **카탈로그 심벌의 실제 범위**: R6b에서 세었다(8.3절). S-101은 지금 읽는 범위 안에 있고, S-131·S-411·S-412는 밖에 있는 것이 있다.

### 8.1 R6-0에서 본, 고치지 않은 것

- **곡선의 억제 표시는 프레임마다 지워지지 않는다.** `SuppressSharedCurves`가 켠 표시(`SCurve::SetSuppress`)는 데이터셋을 읽을 때만 꺼진다. 같은 조건으로 다시 그리면 결과가 같아서 드러나지 않지만, 피처 종류를 끄거나 축척이 바뀌어 "먼저 그리는 쪽"이 사라지면 그 곡선은 아무도 그리지 않는다. 옮기기 전과 같은 동작이다.
- **억제를 거는 조건이 경로마다 다르다.** 셀 하나를 그리는 경로는 제품과 무관하게 억제하고, 묶음·`onIC` 경로는 S-101에만 건다.
- **`DrawS100Layer` 등의 `offset` 인자는 쓰이지 않는다**(경도 한 바퀴 옆의 복사본을 그리려던 자리). 시그니처는 그대로 두었다.
- **수심 가림은 `DrawingStages`의 D2D 구현에 있다.** Skia 프레임에는 빠진다(R7에서 `IRenderer`의 클립으로).

**허용 오차(경로)**: 한 바퀴 호를 뺀 조건에서 "1픽셀 어긋남을 봐준 뒤 1.5% 이하"를 경로의 기준으로 둔다(최대 1.117%). 원을 그리는 지금 코드는 D2D와의 비교에서 이 기준을 넘는 셀이 있고(원 때문), 그것은 의도한 차이다. R6f에서 D2D 쪽 기준 그림을 낼 때 한 바퀴 호를 같은 조건으로 맞출지 정한다.

- `SkiaRenderer`의 생성자는 캔버스만 받는다. `SkiaResources`는 넣을 것이 생기는 R6b(심벌)·R6c(서체)에서 더한다.

- 연산별 작은 그림(4절의 2)은 만들지 않았다. 808개 셀의 경로 그림으로 충분히 갈렸다고 보았다. 심벌·글자에서 필요해지면 만든다.

### 8.3 R6b의 측정과 심벌 파일의 범위

**D2D 대 Skia, 경로와 심벌** (조건은 8.2와 같다. 한 바퀴 호는 원으로 그린다):

| | 중앙값 | 90% | 99% | 최대 |
|---|---|---|---|---|
| 달라진 픽셀 | 0.589% | 1.501% | 2.345% | 4.994% |
| 1픽셀 어긋남을 봐준 뒤 | 0.493% | 1.307% | 2.025% | 4.629% |

- 경로만일 때(중앙값 0.073%)보다 크다. 확대해 보면 **모양과 위치는 같고**, 다른 것은 가는 선(심벌의 선은 대개 0.32 mm = 1.2픽셀)의 안티에일리어싱이다 — 같은 선이 D2D에서는 조금 더 진하고 좁게, Skia에서는 더 옅고 넓게 번진다. 심벌이 빽빽한 영역 하나에서 잉크의 양(바탕과의 차이의 합)을 재면 두 백엔드가 1.7% 안에서 같다. 수심 숫자가 심벌이라 화면 대부분에 이 차이가 깔린다.
- "1픽셀 어긋남을 봐준 수치"는 진하기의 차이를 봐주지 않는다. 가는 선에서는 이 수치가 모양의 차이를 가려내지 못하므로, 심벌은 사람이 보는 것(R6f)과 잉크의 양으로 본다.
- 가장 다른 셀 둘은 여전히 전방위 등화의 원 때문이다(8.2).

**D2D의 읽기와 달라진 것** (결정 4: 명백한 결함은 고친다):

- **경로의 `M`이 둘 이상**: D2D의 `SVGReader`는 경로의 숫자를 전부 한 꺾은선으로 잇는다. 그래서 `M -2,0 M -1.66,-1.6 L ...`의 첫 점이 도형에 끼어든다. 중립 읽기는 `M`마다 새 도형을 시작한다. S-101에서 20개 심벌(BCNTOW22~50, BOYCAN30·31, BOYPIL22~50, EMCOLREG, EMMARS01)이 해당한다 — 색 띠의 모서리가 달라진다.
- **`Z`**: D2D는 닫지 않는다. S-101에서 `Z`가 있는 경로 250개는 모두 채움이라 그림은 같다(채움은 열린 도형도 닫힌 것으로 친다).
- **사각형**: D2D는 첫 점을 다시 찍은 열린 꺾은선, 중립 모델은 닫힌 도형(모서리 하나의 이음이 다르다).
- **굵기가 없는 긋기**: 그리지 않는다(D2D도 굵기 0으로 그려 보이지 않는다. Skia에서 굵기 0은 헤어라인이라 그대로 넘기면 선이 생긴다).
- D2D가 읽고도 쓰지 않는 것(`transform`의 회전, `stroke-dasharray`)은 읽지 않는다.

**넓힌 것**: 상대 명령(`m`, `l`)과 `H`·`V`·`h`·`v`·`z`. 곡선(`C`, `Q`)과 호(`A`)는 읽지 않는다 — 그 명령을 만나면 경로를 거기까지만 두고 `SymbolPicture::unsupported`에 센다.

**심벌 파일 전체를 센 것** (`ProgramData/PC` 아래 27개 카탈로그, `<svg>`의 자식만):

- S-101(718개 파일): `rect`, `path`, `circle`뿐. 경로 명령은 `M`·`L`·`Z`뿐. **읽지 못하는 것이 없다**(테스트로 고정).
- S-131(126개): `<g>` 7개(그 안의 도형 35개는 읽지 않는다 — D2D도 같다), 곡선 명령 `q`·`Q`·`c`·`C`가 있는 경로.
- S-411(49개): `polygon` 20개, `polyline` 68개, `text`, `<g>`, 호 명령 `A` — 대부분 지금 범위 밖이다. D2D도 그리지 않는다.
- S-412(83개): 곡선 `C` 하나.
- 나머지 카탈로그는 `M`·`L`·`Z` 범위 안이다(S-121·S-123·S-413은 `transform`이 있는 경로가 있다 — 회전이 적용되지 않는다. D2D도 같다).

이 범위를 넓히는 일(`<g>`, `polygon`·`polyline`, 곡선, `transform`)은 R6 밖의 별도 항목이다. S-101 그림에는 영향이 없다.

- **위치와 크기는 맞는다.** 확대해 본 곳(`EAST SEA`처럼 가운데 맞춘 글자, 수심 옆의 지명)에서 글자가 같은 픽셀 열에서 시작하고 끝난다. 맑은 고딕은 hhea와 OS/2 win의 어센트·디센트가 같아(2229/495, 줄 간격 0) DirectWrite와 FreeType이 같은 줄 높이(크기 × 1.330)를 낸다. **다른 서체에서는 두 표가 다를 수 있고 그러면 세로 위치가 달라진다**(재 보지 않았다).
- **진하기가 다르다.** D2D는 ClearType(부화소, 색 번짐)에 대비 보정이 있어 작은 글자가 진하다. Skia는 회색조이고 가는 획이 두 픽셀에 걸쳐 옅게 나온다. 표면의 글자 대비를 최대로 올려 조금 줄였고(대비 0.5 → 1.0), 힌팅(`kSlight`)은 눈에 띄는 차이가 없어 끈 채로 두었다. 그래도 Skia 쪽이 옅다 — **읽기에 충분한지는 사용자가 보아야 한다**(R6f). 더 진하게 하려면 LCD 부화소 렌더링을 켜는 길이 있다(표면의 화소 배열을 알아야 하고 화면에 따라 달라져, 설계 3.1은 쓰지 않기로 했다).
- 글자가 빽빽한 셀(`101KR004F4G10` 16%)은 글자 픽셀이 거의 전부 "다른 픽셀"로 잡힌 것이다. 이 수치는 글자에 대해서는 "글자가 얼마나 많은가"를 재는 셈이라 허용 오차로 쓸 수 없다. 글자의 기준은 위치(상자의 시작과 끝)와 사람의 확인으로 둔다.

**설계와 달라진 것 / 남은 것**:

- 서체는 `SkiaResources`가 아니라 `SkiaFonts`(파일 목록)로 받고 `SkiaResources`가 그것을 가리킨다.
- `SkiaImage`의 글자 대비는 메모리 표면에만 해당한다. 응용 프로그램이 제 표면을 쓰면 그 표면의 설정을 따른다.
- 커닝: DirectWrite의 레이아웃은 서체의 커닝을 적용하고 Skia의 `drawSimpleText`는 하지 않는다. 폭이 달라지는 글자 쌍이 있는지 재 보지 않았다(맑은 고딕의 라틴 글자에서 눈에 띄는 차이는 보지 못했다).
- 글자 조합(아랍·인도계 문자)과 양방향: 없다(2절). HarfBuzz·ICU를 켜는 포트 기능으로 나중에 더한다.
- 서체 파일을 어디서 얻는가는 응용 프로그램의 일이다. 패키지는 서체를 싣지 않는다(결정 2).

### 8.5 R6e의 측정과 D2D와 달라진 것: 선 스타일

**자리**: D2D와 Skia 각각에서 선 스타일을 켰을 때 달라지는 픽셀을 뽑아 서로 대조했다(표본 101개 셀 중 선 스타일이 있는 10개). 1픽셀 안에 짝이 없는 픽셀의 비율이 중앙값 3.1%, 90% 9.0%, 최대 10.6%. 확대해 보면 대시와 심벌이 같은 자리에 같은 모양으로 놓이고, 다른 것은 굵기다.

**굵기**: D2D는 띠를 비트맵으로 만들어 선분마다 돌려 찍는다(선형 보간). 1픽셀 대시가 비스듬한 선분에서 두세 픽셀로 번져 굵고 흐리게 보인다. 공용 코드는 대시를 경로로 긋기 때문에 1픽셀 그대로 선명하다. 선 스타일이 그린 픽셀 수는 Skia가 D2D의 0.81배(중앙값)다. **눈에 띄는 차이라 사용자가 보아야 한다**(R6f) — 대시를 카탈로그의 펜 굵기로 긋는 일(결정 4에서 따로 묻기로 한 것)과 함께 정하면 된다.

**D2D와 일부러 다르게 한 것**(결정 4):

- **선분 길이가 간격의 정확한 배수일 때**: D2D는 그 선분을 그리지 않는다(`fmodf(length, width) == 0`). 그린다.
- **마지막 간격의 심벌**: D2D는 띠 비트맵을 선분 끝에서 잘라 심벌이 반쪽이 될 수 있다. 심벌의 자리가 선분 위에 있으면 통째로 그리고, 아니면 그리지 않는다. `IRenderer`에 클립이 없어서이기도 하다(R7에서 클립이 생겨도 반쪽 심벌로 되돌릴 이유는 없다고 본다).
- **띠의 높이로 잘리던 심벌**: D2D는 띠 비트맵의 높이(첫 심벌의 상자에서 계산)를 넘는 부분을 자른다. 자르지 않는다.
- **복합 선 스타일**(`INDHLT02`, `SCLBDY51`): D2D는 100×100 비트맵에 선을 y = 오프셋/0.32에 그리고 그 비트맵을 선에 가운데 맞춰 찍는다 — 선들이 선에서 50픽셀 떨어져 그려지고 100픽셀마다 이음매가 생긴다. 결함으로 보고, 선에서 오프셋만큼 떨어진 나란한 선으로 그린다. 구성 선의 대시는 읽지 않는다(둘 다 간격 전체가 대시다). 808개 셀에 이 두 스타일이 쓰였는지는 세지 않았다.

**그대로 둔 것**(결정 4: 먼저 그대로):

- 띠가 선분마다 처음부터 다시 시작한다(꺾이는 곳에서 무늬가 끊긴다).
- 대시가 펜 굵기와 무관하게 1픽셀이다.
- 선을 따라가는 길이는 mm당 6.25픽셀인데 심벌은 mm당 5픽셀(표시 심벌 배율)로 그린다 — 심벌이 대시에 비해 작다.
- 간격의 길이를 정수 픽셀로 버린다(대시와 심벌의 자리는 버리지 않는다).
- 화면 밖으로 길게 나가는 선분도 전부 놓는다(자르지 않는다).

### 8.6 R6f의 측정: 프레임 시간

KOR TDS 808개 셀, 1600×1000. 셀마다 첫 프레임 뒤의 네 프레임을 평균하고 셀에 걸쳐 더했다. 한 번에 하나씩 돌렸다. Skia의 프레임은 뷰가 보여 주는 것을 모으는 데서 마지막 글자까지(표면 지우기 포함, PNG 쓰기 제외), D2D의 프레임은 뷰어의 `Draw` 한 번이다.

| 백엔드 | 첫 프레임의 합 | 다음 프레임의 합 | 중앙값 | 90% | 최대 |
|---|---|---|---|---|---|
| Skia, CPU, Windows (vcpkg가 MSVC로 빌드) | 136.8 s | 134.0 s | 152 ms | 281 ms | 1673 ms |
| Skia, CPU, Linux 컨테이너 (vcpkg가 GCC로 빌드, 같은 PC) | 25.2 s | 24.1 s | 25 ms | 54 ms | 350 ms |
| Direct2D, 소프트웨어 렌더 | 41.9 s | 32.2 s | 35 ms | 65 ms | 412 ms |
| Direct2D, 디스플레이 어댑터(뷰어의 기본) | 213.9 s | 49.8 s | 44 ms | 87 ms | 661 ms |

- **GCC로 빌드한 Skia는 CPU만으로 D2D보다 빠르다**: D2D 소프트웨어의 0.75배, 뷰어 기본(어댑터)의 0.48배 시간. Docker(WSL2) 안에서 잰 것이라 Windows에서 같은 코드가 내는 수치는 아니지만, 같은 PC의 같은 CPU다.
- **MSVC로 빌드한 Skia는 그 5.6배 느리다.** 원인은 Skia 쪽에 있다: `src/opts/SkRasterPipeline_opts.h`가 컴파일러가 Clang도 GCC도 아니면 `SKRP_CPU_SCALAR`를 정의한다 — 픽셀을 처리하는 경로가 SIMD 없이 컴파일된다. 무늬 채움 하나(`101KR003G2M00`: 넓은 면 하나를 무늬로 채운다)가 MSVC 빌드에서 107 ms, GCC 빌드에서 6 ms다. vcpkg의 Skia 포트는 Windows에서 MSVC를 쓴다(`win_vc`).
- 원인을 찾기 전에 시도한 것(효과 없어 되돌렸다): 심벌을 `SkPicture`로 한 번 기록해 다시 쓰기, 무늬 타일을 기록한 그림이 아니라 비트맵으로 — MSVC 빌드에서 두 가지 모두 시간이 그대로였다. 그리는 준비가 아니라 픽셀을 채우는 쪽이 느렸기 때문이다. GCC 빌드에서 이 두 가지가 도움이 되는지는 재지 않았다.
- 종류별(MSVC 빌드, `101KR002F4000`, 프레임 611 ms): 심벌·무늬·선 스타일을 빼면 165 ms, 글자까지 빼면 134 ms. 심벌 5,169개에 약 370 ms.
- D2D의 어댑터 경로는 첫 프레임이 특히 느리다(합 213.9 s). DC 렌더 타깃이라 프레임마다 GDI 표면으로 되읽는 비용이 있고, 이 PC에서는 소프트웨어 렌더보다 느렸다.

**이것이 뜻하는 것**: 성능에서 Skia가 D2D를 대신하는 데 걸림돌은 Skia 자체가 아니라 **Windows에서의 빌드**다. R7 전에 Windows의 Skia를 clang-cl로 빌드하는 길을 확인해야 한다(이 PC에는 clang-cl이 설치되어 있지 않아 재 보지 못했다). 길은 셋으로 보인다: vcpkg 포트를 오버레이해 `clang_win`을 주기, clang-cl 트리플렛, 또는 뷰어는 GPU 표면을 쓰기(결정 7). vcpkg 레지스트리에 올라가는 `opens100` 포트는 소비자가 받는 Skia를 고를 수 없으므로, 이 문제는 포트의 사용 안내에도 적어야 한다.

**기준 그림에 대한 주의**: R6a~R6e의 단계별 비교는 테스트가 중립 프레임(`DrawingOrder`)으로 `D2DRenderer`에 직접 그린 그림을 기준으로 썼다. 이 그림은 뷰어가 실제로 그리는 그림과 조금 다르다 — 모든 종류를 켠 테스트의 그림과 뷰어의 그림을 대조하면 달라진 픽셀이 중앙값 0.06%, 99% 0.8%, 최대 1.7%(`101KR004F2K30`)다. 원인은 찾지 않았다(후보: 뷰어 쪽의 피처 켜기/끄기 걸러내기, S-98 수심 가림, 글자 묶음 앞의 붓 설정). 위의 최종 비교는 뷰어의 실제 그림으로 했으므로 결론은 그대로지만, R7에서 뷰어를 옮기기 전에 이 차이가 무엇인지 알아야 한다.

**(2026-11-24 추가) 원인을 찾았다**: [R7 설계 7.1](2026-11-24-r7-viewer-on-skia-design.md). 테스트가 캔버스를 지우지 않고 다섯 프레임을 겹쳐 그린 것(뷰어 그림 쪽의 잘못)과, 광선이 변환을 정하지 않아 훅 없는 프레임에서 빠진 것(중립 프레임과 Skia 쪽의 잘못)이었다. 이 절의 "뷰어의 그림 대 Skia" 수치는 두 잘못이 든 그림끼리의 것이다.

### 8.7 R6의 판정에 남은 것

Skia가 KOR TDS 808개 셀을 화면 없이 그리고(결정 3의 조건 첫째), Linux에서도 그린다(셋째). 둘째 — "D2D와의 차이가 정한 기준 안" — 은 경로에 대해서만 수치 기준이 있고(8.2: 1.5%), 심벌·글자·선 스타일은 수치가 모양을 가려내지 못해 사람이 본다고 적었다(8.3~8.5). 사용자가 볼 것:

1. 전방위 등화의 원(8.2) — 원으로 두기로 이미 정했다. 전체 그림에서 다시 본다.
2. 글자의 진하기(8.4) — 회색조 + 최대 대비로 충분한가, LCD 부화소를 켤 것인가.
3. 선 스타일의 굵기(8.5) — 1픽셀 그대로인가, 카탈로그의 펜 굵기를 따를 것인가.

그리고 9번 결정(Windows의 Skia 빌드) — 8.8절에서 길을 확인했다.

### 8.8 Windows의 Skia를 clang-cl로 빌드 (2026-11-24, 실험)

**결과: 다섯 줄로 된다. clang-cl로 빌드한 Skia는 Windows에서 D2D보다 빠르다.**

- Skia의 GN 빌드는 `clang_win="<LLVM 폴더>"` 인자 하나로 Windows에서 clang-cl과 lld-link를 쓴다(`gn/BUILDCONFIG.gn`, `gn/toolchain/BUILD.gn`). vcpkg의 Skia 포트는 이 인자를 주지 않는다.
- 실험: vcpkg의 `ports/skia`를 저장소 밖에 복사하고 `portfile.cmake`의 `win_sdk` 줄 뒤에 다음을 더해 오버레이 포트로 썼다(`-DVCPKG_OVERLAY_PORTS=`). 다른 것은 바꾸지 않았다.

  ```cmake
  vcpkg_find_acquire_program(CLANG)
  get_filename_component(CLANG_WIN "${CLANG}" DIRECTORY)
  get_filename_component(CLANG_WIN "${CLANG_WIN}" DIRECTORY)
  string(APPEND OPTIONS " clang_win=\"${CLANG_WIN}\"")
  ```

  `vcpkg_find_acquire_program(CLANG)`은 vcpkg가 LLVM(이 PC에서는 21.1.8)을 제 도구 폴더로 가져오게 한다 — 사용자가 LLVM이나 Visual Studio의 Clang 구성 요소를 설치할 필요가 없다. Windows SDK와 MSVC의 헤더·라이브러리는 그대로 쓴다.
- 빌드는 처음에 성공했다. 패키지(MSVC, `/WX`)와 소비자 예제는 고치지 않고 이 `skia.dll`에 링크됐다. 매니페스트 전체 5.8분(MSVC의 Skia로 7.2분이었다), `skia.dll` 7.2 MB(MSVC 5.6 MB).

| 백엔드 (808개 셀, 8.6절과 같은 방법) | 첫 프레임의 합 | 다음 프레임의 합 | 중앙값 | 90% | 최대 |
|---|---|---|---|---|---|
| Skia, CPU, Windows, **clang-cl 빌드** | 24.0 s | 22.5 s | 23 ms | 50 ms | 340 ms |
| Skia, CPU, Windows, MSVC 빌드 | 136.8 s | 134.0 s | 152 ms | 281 ms | 1673 ms |
| Skia, CPU, Linux 컨테이너, GCC 빌드 | 25.2 s | 24.1 s | 25 ms | 54 ms | 350 ms |
| Direct2D, 소프트웨어 렌더 | 41.9 s | 32.2 s | 35 ms | 65 ms | 412 ms |
| Direct2D, 디스플레이 어댑터(뷰어의 기본) | 213.9 s | 49.8 s | 44 ms | 87 ms | 661 ms |

- MSVC 빌드의 0.17배, D2D 소프트웨어의 0.70배, 뷰어 기본(어댑터)의 0.45배 시간이다.
- **그림**: MSVC 빌드의 그림 808장과 대조해 16/255 넘게 다른 픽셀이 한 장에도 없다. 바이트 단위로 같은 것은 4장이다(Windows 대 Linux에서 본 것과 같은, 채널당 작은 차이). Skia가 못 그린 것 0개.

**결정(2026-11-24, 사용자)**: 1 — 저장소에 둔다. 2(microsoft/vcpkg에 제안)는 하지 않았고, 하려면 사용자의 확인이 필요하다. 아래는 그때의 선택지다.

1. 이 저장소에 Skia 오버레이 포트(`ports/skia`)를 둔다 — 뷰어와 이 저장소의 빌드는 바로 빨라진다. vcpkg의 포트가 바뀔 때마다 따라가야 한다(패치 14개와 보조 파일을 복사해 들고 있게 된다).
2. microsoft/vcpkg의 Skia 포트에 이 선택지를 제안한다(기능이나 트리플렛 변수) — 받아들여지면 `opens100` 포트의 소비자도 빠른 Skia를 받는다. 외부에 내는 일이라 사용자의 확인이 필요하고 시간이 걸린다.
3. 둘 다: 1을 먼저 하고, 2가 받아들여지면 1을 지운다.

vcpkg 레지스트리의 `opens100` 포트는 소비자가 받는 Skia를 고를 수 없으므로, 2가 되기 전에는 포트의 사용 안내에 "Windows에서 CPU 래스터는 vcpkg의 기본 Skia로는 느리다"를 적어야 한다. 미확인: 디버그 구성의 실행, x86·arm64, 정적 링크(`x64-windows-static`), CI의 러너에서 `vcpkg_find_acquire_program(CLANG)`이 도는지.
